# Research: Content Ingestion Pipeline

This document records the research and decisions for the ingestion pipeline.

## 1. Docusaurus Content Extraction Strategy

### Decision
We will use `BeautifulSoup` to parse the HTML. The primary content of a Docusaurus page is consistently located within the `<article>` tag. Within the article, main headings (`h1`, `h2`, etc.) will be used to delineate sections and populate the `section_heading` metadata. The script will specifically target the content inside the `<article>` tag and ignore common boilerplate containers like `<nav>`, `<aside>` (for the sidebar), and `<footer>`.

### Rationale
Targeting the `<article>` tag is a robust method for Docusaurus sites, as it's a semantic tag that correctly encapsulates the primary page content. This is less brittle than relying on complex CSS class names, which can change between Docusaurus versions or themes.

### Alternatives Considered
- **Using Docusaurus's internal build artifacts**: This would involve parsing React server components or JSON files. This is significantly more complex and tightly couples our pipeline to Docusaurus's internal architecture, making it brittle.
- **Reading source Markdown files**: As per the plan's choice, we are treating the deployed site as the source of truth to ensure the pipeline is decoupled from the source repository.

## 2. Deterministic ID Generation for Idempotency

### Decision
A unique, deterministic ID for each vector point in Qdrant will be generated by creating a SHA256 hash of a composite key: `hash(page_url + chunk_content)`. The `page_url` ensures uniqueness across pages, and the `chunk_content` ensures uniqueness for different chunks on the same page.

### Rationale
This approach guarantees idempotency. If the pipeline is run again on unchanged content, the exact same hashes will be generated for the exact same chunks. When these IDs are used for the `upsert` operation in Qdrant, Qdrant will simply overwrite the existing points with identical data, effectively resulting in no change and preventing duplicates. A simple integer ID would not be deterministic across runs if the page order changes.

### Alternatives Considered
- **Using `uuid.uuid5()`**: This is another good option that creates a deterministic UUID from a namespace and a name. Hashing provides a similar level of determinism and is conceptually simpler.

## 3. Qdrant Batch Upsert Strategy

### Decision
We will use the `qdrant_client.upsert()` method with a batch size of 100-256 points per request. The script will accumulate points and send them to Qdrant in batches.

### Rationale
Batching is critical for efficient data insertion into Qdrant. A single request per point would be extremely slow due to network overhead. A batch size of 100-256 is a common best practice that provides a good balance between upload speed, client-side memory usage, and not overloading the Qdrant service with a single massive request. The `qdrant-client` is optimized for this type of batch operation.

### Alternatives Considered
- **Single-point uploads**: Inefficient and slow for any significant amount of data.
- **Very large batches (e.g., 5000+)**: Can consume significant client-side memory and may lead to request timeouts or performance issues on the Qdrant server, especially for smaller instances.
